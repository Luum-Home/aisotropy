# ADR-0002 — Anti-framework-magic: discard LangChain, struct as single contract

## Status

**✅ Accepted — retroactive formalization (2026-07-08).** Aisotropy discards LangChain and
frameworks in its family for the core, and instead makes **a single Go struct** the source of
truth for HTTP validation, the generated OpenAPI schema, and the JSON Schema enforced on the
LLM. Listed in [docs/decisions/index.md](index.md) as "accepted" since that index was written,
with no corresponding ADR file. This document is that missing file.

## Context

[docs/vision/thesis.md](../vision/thesis.md) states the problem this decision answers: building
an *enterprise* AI chat/agent — not a demo — demands four things that "magic" frameworks
(LangChain and family) sabotage:

1. **Token cost/efficiency** — heavy frameworks bloat prompts with hidden templates, inject raw
   RAG with no reranking, and enter invisible reasoning loops that swallow thousands of tokens
   for a single question; you don't know what string went to the API.
2. **Governance and hallucination mitigation** — prompt engineering alone isn't enough; you need
   input/output guardrails and a structured self-repair loop.
3. **Standard observability** — traces per token/cost/tenant following OTel Semantic
   Conventions for LLMs, not proprietary black-box telemetry.
4. **Multi-tenancy with real isolation** — every byte, token, and millisecond attributable to a
   `tenant_id`/`user_id`, with no context leaks between concurrent requests.

[docs/decisions/index.md](index.md) records the resulting decision plainly: *"Discard LangChain
for its overhead, hidden prompts, and invisible token loops."*

## Goals / Non-goals

**Goals**

- Reject frameworks whose prompt assembly, retrieval, and reasoning steps are opaque to the
  developer ("magic code": automated, costly design decisions a framework makes for you).
- Establish the Go struct as the **single source of truth** governing three things at once: HTTP
  input validation (via [Huma](../components/huma-api.md)), the autogenerated OpenAPI 3.1
  schema, and the JSON Schema enforced on the LLM via structured outputs (via
  [Gollem](../components/gollem-orchestrator.md)).
- Make "you build the payload, you see every token" a structural property, not a best-effort
  discipline.

**Non-goals**

- **Not** rejecting agent orchestration outright — Gollem is adopted precisely (per
  [ADR-0002 note in the decisions index](index.md) and
  [ADR-0010](0010-gollem-adoption-scope-and-observability.md)) *because* it doesn't hide the
  final prompt or introduce invisible reasoning loops, unlike LangChain and family.
- **Not** re-deciding which specific orchestration library to adopt in Go — that is
  [ADR-0010](0010-gollem-adoption-scope-and-observability.md)'s scope; this ADR only fixes the
  anti-magic stance and the struct-as-contract principle that ADR-0010 is evaluated against.

## Options considered

### Option A — Adopt a "magic" framework (LangChain or family) — discarded

Fast to prototype, large ecosystem of pre-built chains/agents/retrievers. Discarded because it
violates all four requirements above: hidden prompt templates and invisible retrieval/reasoning
loops make token cost unpredictable and unauditable; there is no native equivalent to
`ctx`-propagated tenant isolation; and the abstraction layer sits between the developer and the
literal string sent to the LLM, which the project's stance treats as a **design bug** — *"if you
don't know what string was sent, it's a design bug"*
([principles](../vision/principles.md#derived-operating-principles)).

### Option B — No framework at all, hand-rolled HTTP + LLM calls, no shared contract — discarded

Would maximize transparency ("you see every token" trivially, since there's no framework in the
way) but loses the benefit of a single validated schema shared across HTTP, OpenAPI, and the
LLM. Each of the three surfaces (HTTP validation, API docs, LLM structured-output schema) would
need to be defined and kept in sync by hand, reintroducing exactly the kind of drift a single
source of truth is meant to prevent. Not adopted: the project instead builds the
struct-as-contract pattern on top of transparent, non-magic building blocks (Huma), rather than
forgoing schema unification altogether.

### Option C — Struct-as-single-source-of-truth on transparent building blocks (Huma + Gollem) — accepted

A single Go struct, validated once via Huma at the HTTP edge, drives three things simultaneously
per [docs/vision/thesis.md](../vision/thesis.md#the-struct-as-the-single-source-of-truth):

- HTTP input **validation**,
- the autogenerated **OpenAPI 3.1 schema** (a living doc, not hand-maintained),
- the **JSON Schema** enforced on the LLM via structured outputs.

If the LLM breaks the contract, the reflection loop re-requests with the exact typing error
before the client sees anything (Go's equivalent of `FastAPI + Pydantic AI`, per the thesis).
Granular control (middleware + `context.Context`) is solved with traditional software patterns
instead of AI-library abstractions.

## Trade-off comparison table

| Criterion | A — Magic framework (LangChain) | B — No framework, no shared contract | C — Struct-as-contract (Huma+Gollem) — accepted |
|---|---|---|---|
| Token transparency | Poor — hidden templates, invisible loops | Best (trivially, nothing hides it) | Best — you build the payload; the struct is the only source |
| Schema drift risk | N/A (framework owns its own schema surfaces) | High — HTTP/OpenAPI/LLM schema defined and synced by hand | None — one struct drives all three surfaces |
| Governance/guardrails | Framework-dependent, often opaque | Fully manual, easy to skip under time pressure | Structured self-repair (reflection loop) is native to the contract |
| Multi-tenancy isolation | No native `ctx`-based model | Possible, but not enforced by any shared pattern | Native via Huma-extracted `ctx` propagation (see [multi-tenancy](../architecture/multi-tenancy.md)) |
| Time-to-prototype | Fast (large ecosystem) | Slow (everything hand-rolled) | Moderate — less ecosystem, but no schema-sync tax |

## Recommended decision

**Option C is recommended and already implemented.** LangChain and family are discarded for the
core; the struct-as-single-source-of-truth pattern on top of Huma (and, for the LLM side,
Gollem, whose adoption scope is refined separately in
[ADR-0010](0010-gollem-adoption-scope-and-observability.md)) is the standing contract mechanism
for the whole project.

## Consequences

**Positive**

- **Auditable token cost:** every string sent to the LLM traces back to a struct field the
  developer wrote, not a framework template.
- **No schema drift:** HTTP validation, OpenAPI docs, and the LLM's structured-output schema
  can never silently diverge — they're the same struct.
- **Native governance hook:** the reflection loop (bounded retries on schema violation) is a
  direct consequence of the contract being explicit and typed, not an add-on.
- **Consistent with the license/sovereignty stance:** avoids adding a large, fast-moving
  dependency surface whose internals aren't fully inspectable — reinforcing the 100%
  MIT/Apache-2.0, in-process-first stance from [ADR-0001](0001-go-rust-in-process-first-stack.md).

**Negative / technical debt**

- **Less ecosystem leverage:** LangChain's large library of pre-built chains, retrievers, and
  agent templates isn't available; equivalent functionality (retrieval, reranking, routing) has
  to be built or wired in-house.
- **More upfront design work per capability:** each new agent capability needs its own explicit
  struct and contract, rather than reusing a framework abstraction — a deliberate trade of
  velocity for transparency.

## Open questions

1. **Frameworks in adjacent languages/ecosystems.** This ADR discards LangChain specifically;
   whether other Python/JS agent frameworks were evaluated and discarded on the same grounds
   isn't itemized in the surviving source material — only LangChain is named.
2. **Where the anti-magic line is drawn for future dependencies.** The stance is clear
   ("if you don't know what string was sent, it's a design bug") but no explicit checklist for
   evaluating a *new* dependency against that bar exists yet beyond this ADR's reasoning.
