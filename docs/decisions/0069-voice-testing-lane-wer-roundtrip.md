# ADR-0069: Voice testing lane — TTS→STT round-trip gated on WER, without audio hardware

**Status:** Accepted (2026-07-23 — implementation landed with the ADR: `examples/voice-pipecat/tests/`
+ threshold-assert modes on both metric scripts. All thresholds in this ADR are grounded in real
measured runs executed the same day; the measured table is below)
**Delivers:** an automated, hardware-free test lane for the ADR-0066 voice PoC: known text →
Kokoro TTS → faster-whisper STT → assert word error rate under an empirically calibrated
threshold (the audio equivalent of the shim's golden wire test), plus pinned WAV fixtures, a
file-based Pipecat pipeline test (WAV in → captured TTS frames out, no mic/speaker), and
`--assert-*-ms` threshold modes on `measure_ttfab.py` / `measure_bargein.py`.
**Related:** ADR-0066 (the OpenAI-compat shim + the PoC under test), the arena stub/real lane
precedent (`.claude/rules/arena-full-matrix.md`), the deterministic-threshold pattern
(`arenas/live/runner/scoring` — `passQAThreshold`), the voice landscape license table
(`docs/research/voice-pipeline-landscape-2026-07-23.md`).

## Context

ADR-0066 shipped the voice PoC with an honest gap: `bot.py` and the STT/TTS legs were complete,
syntax-checked code that had **never executed end-to-end**, because they need audio hardware and
model downloads. "Run it and listen" is not a regression test. The question this ADR answers:
how does the voice path get TESTED — repeatably, assertably, with no microphone, no speaker, and
no human ear in the loop?

The repo already has the pattern twice over:

- **The wire golden test** (`internal/api/openai_compat_test.go`): the in-repo client consumes
  the in-repo server and the bytes must round-trip. The audio analogue: the PoC's own TTS speaks
  a known sentence, the PoC's own STT must recover it.
- **The arena stub/real lanes** (`.claude/rules/arena-full-matrix.md`): expensive real-model runs
  are a separate, opt-in lane; the free lane proves wiring offline. Voice models (~74MB whisper
  weights + the Kokoro container) belong in exactly such an opt-in lane, never in per-PR
  `go test ./...`.

## Decision

### 1. TTS→STT round-trip gated on WER (`tests/test_roundtrip.py`)

Synthesize ≥3 known sentences (varied length, numbers and proper nouns included — they are the
first casualties of a bad TTS/STT pairing) with Kokoro, transcribe with faster-whisper, and
assert `WER ≤ 0.20` per sentence. WER is computed over normalized word lists (lowercase,
punctuation stripped, hyphens split) so only WORD survival is scored, not formatting.

**The threshold is a measured constant, not a guess** (the `passQAThreshold` pattern: document
the empirical fixtures behind every pass bar). Measured 2026-07-23, Kokoro-FastAPI
`cpu:latest` (voice `af_heart`) → faster-whisper `base.en` int8, macOS arm64:

| Reference sentence | WER | Error content |
|---|---|---|
| "Hello there." | 0.000 | — |
| "The quick brown fox jumps over the lazy dog." | 0.000 | — |
| "In 1969, Neil Armstrong walked on the Moon with Buzz Aldrin." | 0.000 | — |
| "Doctor Rivera scheduled 42 interviews across Barcelona and Montevideo before the deadline." | 0.083 | "Doctor" → "Dr." |
| "The meeting starts at 9 on March 3." | 0.000 | — |
| "Please arrive at gate 7 by a quarter past nine." | 0.100 | "nine" → "9" |

Worst observed error is **formatting** (abbreviation/digit rendering), not intelligibility.
`0.20` = 2× headroom over the worst measured case; a real regression (dropped clause, garbled
number, noise) lands far above it. Calibration model is `base.en`; `VOICE_STT_MODEL=tiny.en`
(~40MB) is documented for memory-constrained machines with the caveat that tiny runs slightly
above the calibrated WER profile.

### 2. WAV fixtures with known transcripts (`tests/test_fixtures.py`) — committed

Three pinned WAVs in `tests/fixtures/` (`greeting`/`pangram`/`numbers`, generated by Kokoro,
~298KB total) each carry a declared transcript; STT must recover it at `WER ≤ 0.15` (tighter
than the round-trip bar because the input is frozen — the only moving part is the STT model;
all three measured 0.000 at calibration). **Decision: the fixtures are COMMITTED, not
gitignored.** Rationale: <1MB total is negligible repo weight, and a pinned WAV keeps the STT
half deterministic even when the TTS voice/model changes underneath — exactly why golden files
are committed anywhere else in this repo. A missing fixture regenerates on first run via the
same TTS backend (and would then be committed as the new pin — a deliberate re-pin, visible in
the diff).

### 3. File-based Pipecat pipeline test (`tests/test_pipeline_file.py`) — no audio device

The bot's exact processor chain (whisper STT → user context aggregator → shim LLM → Kokoro TTS)
runs headless: the utterance enters as `InputAudioRawFrame`s bracketed by the VAD frames a real
transport would emit, and the reply is captured as `TTSAudioRawFrame`s. The seam is
**first-party**: `pipecat.tests.utils.run_test` (BSD-2, ships inside the pipecat package — the
harness pipecat uses for its own unit tests), not a hand-rolled fake transport. Executed
end-to-end against a live aisotropyd (stub LLM, HS256 JWT): WAV in → transcription → shim
streams the reply → TTS frames out, PASSED in 147s.

Findings recorded while building it (all verified against installed source, per
dependency-reuse-first):

- The test targets the **pinned `pipecat-ai>=0.0.60,<0.1` line** and skips on 1.x: pipecat 1.x
  removed `processors/aggregators/openai_llm_context.py`, which `bot.py` imports.
- pipecat 0.0.x cannot install on Python 3.14 (its `numba` dependency has no 3.14 support);
  Python 3.13 works. Documented in the README.
- pipecat 0.0.x's `stt_service` imports `websockets` at module import time but the `[whisper]`
  extra does not pull it — added to `requirements-test.txt` (BSD-3).
- pipecat 0.0.x's `OpenAITTSService` validates `voice` against OpenAI's own voice ids
  (`VALID_VOICES[...]` KeyErrors on a Kokoro id like `af_heart` and degrades into a silent
  no-audio run). The test uses `voice="alloy"`, which Kokoro-FastAPI maps server-side. This is
  also a **latent bug in `bot.py`** (it passes `af_heart` to the same service) — left for a
  follow-on since bot.py changes are outside this change's scope. *(fixed 2026-07-23:
  `bot.py` now defaults `KOKORO_VOICE` to `alloy`, the same mapped id this lane uses.)*

### 4. Metric scripts become threshold asserts

`measure_ttfab.py --assert-ttfab-ms N` and `measure_bargein.py --assert-bargein-ms N` exit
non-zero (1) when the measured MEDIAN breaches the threshold, keeping exit 2 for
configuration/connectivity errors and preserving default behavior exactly (no flag → measure
and report, exit 0). Verified live against the stub-backed shim: PASS path exit 0 (median
llm_ttft 18.1ms, barge-in-to-silence 0.9ms), breach path exit 1 for both scripts. This turns
the ADR-0066 "evidencia ejecutable" scripts into CI-usable gates without changing what they
measure.

### 5. Lane gating: opt-in via `VOICE_LANE=real`, never per-PR

The arena stub/real precedent applied to audio: model-dependent tests run ONLY when
`VOICE_LANE=real` is exported. Without it — or with it but with deps/models/services missing —
every voice test **SKIPs with an actionable reason** (which dependency, which command brings it
up). The lane also self-defers on a saturated machine: the session pre-flights
`scripts/resource-guard.sh` (commit 9e1a5d9) — BLOCKED (exit 3) → skip with reason instead of
an OOM-killed worker; DEGRADED (exit 1) → forced `tiny.en` + 2 CPU threads. Never fails, never
silently passes: `pytest -q` in a bare env reports
`8 passed, 8 skipped` (the 8 passes are the pure-stdlib WER unit tests — the lane's
deterministic floor, safe for any CI). Verified in three environments: full env without
`VOICE_LANE`, pytest-only env without `VOICE_LANE`, pytest-only env WITH `VOICE_LANE=real`
(deps missing → skips, zero failures).

## WER implementation: hand-rolled, not jiwer

`tests/wer.py` is a ~30-line word-level Levenshtein (two-row DP, stdlib `re` only) with its own
unit tests. `jiwer` (Apache-2.0) would pass the license gate, but a transitive dependency is not
worth 30 auditable lines — the same call `arenas/live/runner/scoring` made (pure functions,
stdlib imports only, deterministic by construction).

## TTS backend: Kokoro-FastAPI over HTTP — kokoro-onnx REJECTED (license + broken wheel)

The tests synthesize via the **Kokoro-FastAPI container** (`KOKORO_BASE_URL`), the same
Apache-2.0 service `bot.py` already uses. The in-process `kokoro-onnx` pip package was evaluated
first (it would remove the container dependency) and rejected on two grounds, both verified
empirically on 2026-07-23:

1. **License (decisive):** `kokoro-onnx` hard-requires `phonemizer-fork` — **GPL-3.0** — and
   `espeakng-loader`, which bundles a compiled **espeak-ng (GPL-3.0)** dylib
   (`pip show` + the wheel's own license texts). The repo license gate blocks GPL in
   pip-installed code. Inside the container, the GPL pieces sit behind the separate-service
   boundary the license policy explicitly allows and ADR-0066 already adopted for this exact
   component.
2. **Broken on this platform anyway:** espeakng-loader's macOS arm64 wheel (0.2.0–0.2.4) bakes
   a CI-runner data path into the dylib and ignores the data-path argument
   (`espeak_Initialize`/`espeak_ng_InitializePath` both leave the baked
   `/Users/runner/work/...` path in effect → hard `exit(1)` on first phonemization, reproduced
   via direct ctypes calls). The misaki (Apache-2.0) escape route is blocked too: it requires
   spacy, which does not build on Python 3.14.

Dependency license verdicts for everything the lane adds (`pip show`, 2026-07-23):

| Package | License | Verdict |
|---|---|---|
| pytest | MIT | ✅ |
| soundfile | BSD-3-Clause (libsndfile LGPL-2.1, dynamically loaded, unmodified) | ✅ (CAUTION tier per license policy) |
| websockets | BSD-3-Clause | ✅ |
| faster-whisper / ctranslate2 / onnxruntime | MIT | ✅ (already in requirements.txt path) |
| httpx | BSD-3 | ✅ (already present) |
| kokoro-onnx | MIT itself, but **phonemizer-fork GPL-3.0 + bundled espeak-ng GPL-3.0** | 🚫 NOT ADOPTED |
| jiwer | Apache-2.0 | not needed (hand-rolled WER) |

## Honest boundary (what this lane does NOT measure)

- **WER measures intelligibility, not perceptual quality.** A robotic, mispaced, tonally wrong
  voice can score WER 0.000. "Does it sound good" is MOS/human-listening territory and stays
  manual; this lane only guarantees "the words survive the trip".
- The round-trip couples TTS and STT: a WER pass means the PAIR works; it cannot attribute a
  failure to one side alone (the pinned fixtures isolate the STT side; nothing isolates TTS
  except a human ear).
- One voice (`af_heart`/`alloy`-mapped), one language (en), one STT size (`base.en`) are
  calibrated. Other combinations run but their thresholds inherit no evidence.
- The pipeline test asserts structure (audio frames out, non-trivial duration), not the WER of
  the bot's reply — the stub LLM's reply text is an implementation detail, not a pinned fixture.
- Nothing here wires the lane into CI; it is operator-run (`VOICE_LANE=real pytest tests/`),
  like the arena's real lane.

## Consequences

- The ADR-0066 "complete but never executed" caveat is now closed for the STT/TTS legs: the
  full sandwich (WAV → whisper → shim → Kokoro → audio frames) has an executable, asserted,
  hardware-free regression test, and it has actually passed against the live stack.
- Per-PR CI cost: zero. The lane adds only stdlib WER unit tests to an unconditional run.
- The committed fixtures pin today's Kokoro voice; a TTS upgrade that changes the audio will
  show up as a fixture diff (deliberate re-pin), not a silent behavior change.
- `requirements-test.txt` documents test-only deps with license verdicts; `requirements.txt` is
  untouched except that its pipecat pin's Python ceiling (≤3.13) is now documented.

## Non-goals

- **No MOS / perceptual scoring** — human territory (see honest boundary).
- **No LLM-as-judge of transcripts** — the arena's deterministic-judging rule applies verbatim:
  WER is a pure function; no network/model call decides a pass.
- **No bot.py rewrite** — its `af_heart`-vs-`VALID_VOICES` latent bug and the pipecat 1.x
  migration are named follow-ons, not smuggled into a testing ADR. *(voice-id follow-on fixed
  2026-07-23: bot.py default → `alloy`; the pipecat 1.x migration remains open.)*
- **No CI wiring / no model caching infra** — opt-in lane first; automation is a follow-on once
  the lane has operator mileage.

### Dismissed follow-on (operator decision, 2026-07-27)

- **The GPU / streaming-TTS path: DISMISSED, not deferred.** The 2026-07-23 measurement made
  Kokoro-CPU's first audio byte the sandwich's bottleneck (median TTFAB 3543 ms, of which 3540 ms
  was TTS and 3.1 ms the runtime), and the natural next move looked like the GPU image. Three
  things dissolved that:
  - **The hardware does not exist here.** Kokoro-GPU wants CUDA; this is Apple Silicon. Pursuing
    it means a different machine or a remote runner — the only item of the three follow-ons that
    is blocked by hardware rather than by effort.
  - **The premise shrank when re-measured.** The 3540 ms record does not reproduce: re-run native
    on 2026-07-27 with the same function, the same stack answers **1647 ms** short / **2135 ms**
    long. Much of the original figure was machine state — that run happened at ~90 % swap under
    several concurrent agent sessions — not model cost. Optimising against an inflated number is
    how effort goes to the wrong place.
  - **A CPU path already beats what GPU was meant to buy.** The voicebox spike measured **410 ms**
    warm on CPU (`docs/06-Daily/reports/voicebox-spike-2026-07-27.md`), and voicebox has since
    been adopted as the PoC's audio backend. The remaining gap does not justify new hardware.

  What would revive it: a target that a CPU backend genuinely cannot meet (sub-200 ms first audio
  byte, or many concurrent sessions per host — voicebox serialises inference at one call per
  instance, measured wall/serial-sum 1.13), on a machine that has the GPU to test it on. Recorded
  here rather than carried as open debt, because an item nobody can act on is not a plan.
