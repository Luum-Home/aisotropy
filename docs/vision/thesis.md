# Thesis

## The problem

Building an *enterprise* AI chat/agent — not a demo — demands four things that "magic"
frameworks (LangChain and family) sabotage:

1. **Token cost/efficiency.** Heavy frameworks bloat prompts with hidden templates,
   inject raw RAG with no reranking, and enter invisible reasoning loops that swallow
   thousands of tokens for a single question. You don't know what string went to the API.
2. **Governance and hallucination mitigation.** Prompt engineering alone isn't enough:
   you need input/output guardrails and a structured self-repair loop.
3. **Standard observability.** Traces per token/cost/tenant following OTel Semantic
   Conventions for LLMs — not proprietary black-box telemetry.
4. **Multi-tenancy with real isolation.** Every byte, token, and millisecond attributable
   to a `tenant_id`/`user_id`, with no context leaks between concurrent requests.

## The stance: zero magic

The declared enemy is **"magic code"**: automated, opaque, costly design decisions that a
framework makes for you. Aisotropy inverts the relationship: **you build the payload, you
see every token.** The framework is a *clean bridge* between your code and the LLM, not an
abstraction that gets in the way.

The technical consequence is that **granular control is native, not a feature**: it's
solved with traditional software patterns (middleware + Go's `context.Context`) instead of
AI libraries.

## The struct as the single source of truth

The piece that ties everything together. A single Go struct — via [Huma](../components/huma-api.md)
at the HTTP edge and [Gollem](../components/gollem-orchestrator.md) for the LLM — governs
**three things at once**:

- the **validation** of the HTTP input,
- the autogenerated **OpenAPI 3.1 schema** (living doc),
- the **JSON Schema** enforced on the LLM via structured outputs.

If the LLM breaks the contract, Gollem's *reflection loop* re-requests with the exact
typing error, before the client sees anything. It's the Go equivalent of
`FastAPI + Pydantic AI`.

## Tiered memory

The real differentiator isn't the LLM: it's how the system remembers. Memory is divided by
**"temperature" and access cycle**, like a computer's memory hierarchy. See
[tiered memory](../architecture/memory-tiers.md). This connects directly to Karpathy's
**"LLM OS"** model ([principles](principles.md)).

## Sovereignty

**100% MIT/Apache-2.0** stack — zero BSL or commercial licenses. Everything runs on your
own hardware, in-process where possible, with megabyte-sized native binaries (not gigabytes
of JVM). Your data, your infrastructure, auditable end to end. See the
[stack overview](../architecture/overview.md).

## What it is and isn't

| Is | Isn't |
|---|---|
| A typed, in-process, per-request agent runtime. | A declarative data pipeline (that would be [Bento](../decisions/index.md), a future radar item). |
| Optimized for interactive chat (SSE, minimal TTFT, ctx cancellation). | Optimized for massive batch ingestion (for that, async workers / DataFusion). |
| Adaptive per-user memory with self-improving primitives. | Per-user executable code cloning (only *metadata* is cloned: prompts, descriptions, few-shots). |
| Purely sovereign and open source. | Dependent on a cloud or proprietary SDK. |
