--------------------------------------------------------------------------------
BROKER RANKING (for aisotropy's outbox -> broker -> consumer path)
--------------------------------------------------------------------------------
1. NATS JetStream  [Apache-2.0]  — RECOMMENDED DEFAULT. Sub-ms p50, push
   delivery (no client poll interval), native id-dedup, server-side per-tenant
   subject filter. Simplest single-binary op. Passes the license gate.
2. Valkey Streams  [BSD-3-Clause] — fastest here (sub-ms p50, ~40k msg/s). Great
   if Valkey is already in the stack. Redelivery leans on PEL + same-consumer-id
   reclaim (or XAUTOCLAIM); slightly more app-side care than JetStream. Passes gate.
3. Apache Kafka    [Apache-2.0]  — the gate-passing Kafka-API option. Correct on
   every property, but single-node JVM Kafka showed the highest and most VARIABLE
   latency here (p50 65ms..994ms) and the lowest throughput. A tuned/multi-broker
   Kafka is a different animal; this is a single-node dev result. Passes gate.
4. Redpanda        [BSL]  *** LICENSE-GATE BLOCKER — NOT ADOPTABLE w/o ADR ***
   Same Kafka client (franz-go) and API as #3, with much lower/steadier latency
   and higher throughput than single-node Kafka — but the SERVER is Business
   Source License, a 🚫 BLOCKER per .claude/rules/cos/license-policy.md. Measured
   only because the operator asked. Its speed argues for tuning Kafka or choosing
   NATS, NOT for adopting a BSL server. The Apache-2.0 Kafka server is the
   drop-in, gate-passing substitute for identical client code.

MEASUREMENT CAVEATS (honest):
 - Kafka/Redpanda latency is sensitive to franz-go FetchMaxWait (set to 20ms
   here). Under a saturating 8-worker publish burst, the slower-throughput broker
   (single-node Kafka) becomes backlog-bound, so its "latency" partly reflects
   queue wait, not broker RTT. This is why Kafka's p50 swings run-to-run.
 - NATS uses a push consumer (no poll interval); Valkey uses batched XREADGROUP +
   one XACK per read. These consumer models differ, so cross-broker latency is
   apples-to-oranges at the margin. Correctness properties are model-independent.
 - Single node, RF=1, no fsync tuning, contended host. Not a capacity statement.

floci.io (cloud-managed-queue local path): DOCUMENTED, NOT MEASURED in this run.
See README "floci.io" — it is the MIT local-emulation lane (dev/test) for a future
SQS/SNS/Service-Bus/Pub-Sub managed-queue adapter. Production stays on a
self-hostable, gate-passing broker (NATS JetStream or Apache Kafka).
