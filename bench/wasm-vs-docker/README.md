# wasm-vs-docker benchmark

Head-to-head measurement of the **WASM pure-compute isolation tier** (wazero, via
`internal/sandbox.WASMProvider` over `internal/wasmtool`) against the **container
"hands" tier** (`internal/sandbox.DockerProvider`) for the **same trivial work** —
a JSON→JSON echo tool. It is the Phase-2 companion to `bench/footprint/` and
grounds the "add a WASM provider for cheap per-call pure-compute isolation"
recommendation (`docs/research/wasm-vs-docker-sandbox-2026-07-17.md` §4.1, §6) in
repo numbers rather than vendor blogs.

## What it measures

Per candidate (`wasm`, `docker`), holding work constant (a trivial echo):

| Metric | WASM method | Docker method |
|---|---|---|
| **Cold start / first dispatch** | `Load` (compile module) + first `Dispatch` | `Create` (`docker run -d`) + first `Exec` |
| **Warm per-op throughput** | N sequential fresh-instance dispatches → ops/s + p50/p95/p99 | N sequential `docker exec` → ops/s + p50/p95/p99 |
| **Host RSS per live instance** | process RSS delta to hold one compiled tool live in-process | one idle container's `docker stats` memory |

## Honesty gates (why the numbers are trustworthy — and their limits)

- **The WASM tier serves only the pure-compute (JSON→JSON) subset.** It **cannot**
  run the coding-agent hands: WASI has no `fork`/`exec` — that is precisely why the
  container tier stays. This bench compares the two on the pure-compute work they
  can *both* do; it is **not** a claim that WASM replaces Docker.
- **Docker warm N is smaller by default** (`-docker-n 200` vs `-n 10000`): each
  `docker exec` forks the docker CLI and attaches to containerd (~tens of ms), so a
  10k-exec run is impractically slow. The reduced N is printed next to the number,
  not hidden.
- **The WASM guest is a Go/wasip1 module** and therefore bundles the whole Go
  runtime (~3–4 MiB). The harness prints the module size and notes that a
  hand-written WAT/Rust guest would be far smaller, and that the compiled module is
  **shared** across dispatches — only per-call linear memory is transient.
- **WASM 3.0 rows (WasmGC / memory64) are UNBENCHMARKABLE on wazero v1.12.0**
  (Core 1.0/2.0 only; memory64 is open request `wazero#2452`). The harness emits an
  explicit `N/A — not shipped in wazero` line rather than faking a row. Running it
  would require switching to a CGO-bearing runtime (wasmtime/WasmEdge), breaking the
  single-static-binary posture, purely to produce the row.
- **The Docker path skips cleanly** when the `docker` CLI or the image is absent.

## Reproduce

Run from the **repo root** (the harness shells out to `go build GOOS=wasip1` to
compile the guest, and resolves `bench/wasm-vs-docker/testdata/guest` relative to
the CWD):

```sh
# default: WASM N=10000, docker N=200, 5 cold-start samples, image alpine:3.20
go run ./bench/wasm-vs-docker

# tune sample sizes
go run ./bench/wasm-vs-docker -n 10000 -docker-n 200 -cold-runs 5

# WASM only (no Docker needed)
go run ./bench/wasm-vs-docker -skip-docker

# different local image (must already be present; no pull is forced)
go run ./bench/wasm-vs-docker -image alpine:3.20
```

Raw output is written to `bench/wasm-vs-docker/results.txt` and echoed to stdout.

## Docker hygiene

The harness creates containers named `aisotropy-sbx-wasmbench-*` and removes every
one it creates (`Close` per container + `DockerProvider.CleanupAll` on exit). It
**builds and pulls no images** — it uses a local image you already have (default
`alpine:3.20`), so there is nothing to `docker rmi`. It never touches
service containers (`aisotropy-rqlite-1`, `aisotropy-qdrant-1`, etc.).

## Files

- `main.go` — the harness (package `main`).
- `testdata/guest/main.go` — the constant-work WASM guest (`//go:build wasip1`;
  under `testdata/` so the go tool ignores it for normal builds/vet — it only
  compiles under `GOOS=wasip1 GOARCH=wasm`, which the harness does at run time).
- `results.txt` — raw measured output (regenerated by a run).
