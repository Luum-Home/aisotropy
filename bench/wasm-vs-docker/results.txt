# BOTTOM LINE — does WASM kill Docker for pure compute? Axis by axis:
#   THROUGHPUT: WASM wins outright, every guest — 1-2 orders of magnitude over
#     docker exec (which forks the CLI + attaches to containerd per call). Not close.
#   COLD-START: the Go guest's uncached 3+ MiB compile is WASM's one soft spot (it can
#     trail a warm docker exec). Both fixes land it decisively ahead: a LEAN guest
#     (TinyGo ~140ms, Rust ~2ms) already beats docker's create+first-exec, and a warm
#     CompilationCache collapses EVERY guest's effective cold-start to single-digit ms
#     or less. So with lean-guest OR warm-cache, WASM wins cold-start too.
#   RSS: the subtle one, read it honestly. A single container's `docker stats` (~1 MiB)
#     can look SMALLER than a lean wasm tool's in-process delta — but that container
#     number EXCLUDES the dockerd/containerd daemon (hundreds of MiB, always resident).
#     The wasm figure is the COMPLETE marginal cost, no hidden daemon, and the wazero
#     engine (~the bulk of the lean-guest delta) is a one-time cost shared across ALL
#     tools in the process. So per-instance-at-scale and full-host-cost, lean-guest WASM
#     wins RSS; the single-container raw stat is the only framing where docker looks
#     smaller, and only because it hides its daemon.
#   -> ANSWER: for pure compute, a LEAN guest (TinyGo/Rust) + warm CompilationCache
#      makes WASM beat Docker on throughput and cold-start outright, and on RSS once the
#      daemon is counted. The Go-runtime-bundling guest was the whole reason the first
#      pass saw a cold-start/RSS loss — swapping it for a lean guest erases it.
#   THE CAVEAT THAT DOES NOT MOVE: this is ONLY the pure-compute (JSON->JSON) subset.
#     The coding-agent hands (shell, git, fork/exec) CANNOT run in WASI — Docker stays
#     the tier for those, no matter how these numbers land. WASM adds a cheap compute
#     tier; it does not delete the container tier.

# READING THE TABLE: `setup` is ONE-TIME (a tool is Load()'ed once, then dispatched
#   many times; a container is `run` once, then exec'd many times) — amortize it over
#   the call volume, AND note the CompilationCache table above collapses it further.
#   `warm ops/s` + p50/p95/p99 are the per-call steady state, the number that scales.

# WASM 3.0 (WasmGC / memory64) row: N/A — UNBENCHMARKABLE on wazero v1.12.0.

# NOTE: docker warm ops/s is over N=200 (not 10000) — each `docker exec` forks the
#   docker CLI + attaches to containerd, so a 10k-exec run is impractically slow.
#   The reduced N is the honest measurement of the same per-op cost, not a shortcut.

# RSS CAVEAT (every number here has one — none is a clean per-instance figure):
#   - WASM 'in-process' RSS is the harness process delta across the Load+warmup of
#     ONE tool. For the go guest it is DOMINATED by wazero compiling the 3+ MiB
#     Go-runtime module (one-time, shared); the tinygo/rust deltas are far smaller
#     because their modules are. A dispatch's linear memory is transient (reclaimed
#     on Close), so none of these is a per-CALL cost.
#   - Docker 'container' RSS is one container's `docker stats` memory; it EXCLUDES
#     the dockerd/containerd host-side memory (hundreds of MiB, shared). So the
#     sub-MiB container figure is not the full host cost of a container either.
